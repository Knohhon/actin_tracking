# Описание данных в `data/`

Дата осмотра: 16 ноября 2026 года. Описание относится к локальному набору `data/v0.2.1/`.

## Назначение и происхождение

Это набор последовательностей изображений филаментов с разметкой отдельных объектов в расширенном формате COCO. Он включает синтетические данные для обучения и валидации, а также реальные изображения. В исходном [README набора](../data/v0.2.1/readme.md) реальные данные названы тестовой выборкой, хотя в именах файлов используется `val`.

Согласно этому README, синтетические изображения получены из ранее созданных аннотаций генератором проекта Bioscope со стилем `trial_370`. Приведённый там код преобразует маску плотности в яркости с добавлением гауссовского шума и возвращает `uint8`. Параметры: средние яркости `56.1`, `111.8`, `147.8`; стандартные отклонения `24.1`, `44.8`, `53.0`.

В метаданных синтетических JSON указаны `contributor: IMM UB RAS` и дата `2026/06/22`, в реальных — `UrFU` и `2024/07/17`. Версия `info.version` внутри JSON — `1.0`; это отдельное поле, не версия каталога `v0.2.1`.

## Изображения и последовательности

| Поднабор | Файлы PNG | Последовательности | Размер кадра по записям `images` |
| --- | ---: | --- | --- |
| Синтетический train | 20 100 | 670 × 30 кадров | 768 × 768 |
| Синтетический val | 300 | 10 × 30 кадров | 768 × 768 |
| Реальные данные | 120 | Три диапазона имён по 40 кадров | 512 × 512 |

Синтетические имена имеют вид `<sequence_id>_<номер кадра>.png`, например `1074658952804_000.png`. Индексы кадров идут от `000` до `029`. Группировка имён файлов и группировка записей JSON по `sequence_id` дают одинаковое количество последовательностей и их длины. Записи `images` в синтетических JSON перемешаны: для временного порядка нужно явно группировать и сортировать кадры.

Реальные файлы названы `100.png`–`139.png`, `200.png`–`239.png`, `300.png`–`339.png`. Непрерывность времени между этими диапазонами при осмотре не устанавливалась.

В каждом каталоге проверены PNG-заголовки трёх файлов: первого, среднего и последнего в списке. Все девять примеров — одноканальные 8-битные изображения (PNG color type `0`); размеры совпадают с разметкой. Это выборочная проверка формата PNG, а не проверка всех изображений.

Визуально просмотрены `train_synt_30_v7_prerendered/1074658952804_000.png` и `val_v1_gray/100.png`. В обоих случаях видны светлые изогнутые нити на тёмном шумном фоне. В просмотренном синтетическом кадре объекты заметно плотнее расположены, а реальный кадр выглядит более размытым; это наблюдение по двум примерам, не статистика всего набора.

## Формат разметки

В просмотренных фрагментах JSON присутствуют разделы `info`, `licenses`, `images`, `annotations`, `categories`. Категория одна: `id: 1`, `name: filament`, `supercategory: microbiological`.

Записи изображений содержат:

- `id` — идентификатор записи изображения;
- `file_name` — имя PNG без каталога; путь нужно строить относительно соответствующего каталога изображений;
- `height`, `width` — размеры кадра;
- `license` — ссылка на запись лицензии;
- `sequence_id` — идентификатор последовательности в синтетической разметке и в `seq_v1_val_real.rle.json`.

В проверенных аннотациях есть `id`, `image_id`, `category_id`, `iscrowd`, `segmentation`, `bbox`, `area`. Поле `image_id` связывает объект с `images.id`. Маска `segmentation` представлена COCO RLE: `size: [height, width]` и строка `counts`. Для получения бинарной маски нужен декодер COCO RLE. `bbox` задаётся как `[x, y, width, height]`, `area` — площадь маски в пикселях.

В просмотренных синтетических аннотациях дополнительно есть `track_id`, предназначенный для связи объекта между кадрами. В просмотренных реальных аннотациях такого поля нет. Полный состав полей всех объектов и целостность треков не проверялись.

Числовые идентификаторы синтетических аннотаций могут превышать безопасный целочисленный диапазон JavaScript `Number` (`2⁵³ − 1`): например, встречается `id: 30909304266160180`. При загрузке нужно сохранять точные целые значения; обычный `JSON.parse` в JavaScript может потерять точность. Значения ID не следует интерпретировать как количество объектов.

В `licenses` указана лицензия `Attribution-NonCommercial-ShareAlike License` со ссылкой `http://creativecommons.org/licenses/by-nc-sa/2.0/`. Здесь зафиксировано содержимое метаданных; внешние условия лицензии не проверялись.

## Два варианта разметки реальных данных

Эти JSON ссылаются на один каталог `val_v1_gray/`, но по-разному представляют изображения.

| Свойство | `seq_v1_val_real.rle.json` | `val_real_seqlen3.rle.json` |
| --- | --- | --- |
| Записей в `images` | 342 | 117 |
| Уникальных `file_name` | 120 | 117 |
| Поле `sequence_id` | Есть: 114 групп по 3 записи | Отсутствует |
| Начало списка | `100, 101, 102`; затем `101, 102, 103` | `100, 101, 102`; затем `103, 104, 105` |
| Использование файлов | Один PNG повторяется в нескольких окнах с разными `images.id` | Каждый используемый PNG встречается один раз |

Первый файл представляет перекрывающиеся трёхкадровые окна: по 38 окон на каждый диапазон из 40 кадров. Число 342 обозначает записи изображений в окнах, а не количество физических PNG.

Во втором файле отсутствуют записи для `139.png`, `239.png`, `339.png`, хотя сами изображения на диске есть. По списку `images` кадры организованы неперекрывающимися тройками, но явного поля последовательности нет.

Исходный README рекомендует первый вариант при `sequence_len > 1`, второй — при `sequence_len = 1`. Таким образом, суффикс `seqlen3` во втором имени сам по себе не определяет режим загрузчика: нужно учитывать реальную структуру записей и способ группировки. Оба файла используют одни и те же реальные изображения, поэтому их нельзя считать независимыми выборками.

## Что проверено и границы осмотра

Проведены перечисление файлов и подсчёт размеров, проверка полного раздела `images` каждого JSON, сопоставление всех указанных имён с файлами на диске. Все ссылки из `images.file_name` разрешаются в соответствующих каталогах.

Крупные файлы полностью не читались: у обучающего JSON прочитаны первые 8 MiB, у остальных JSON — первые 256 KiB; дополнительно у каждого прочитан хвост размером 1 200 байт. Этих начал хватило для извлечения всех записей `images` и первой аннотации. README прочитан полностью. ZIP не распаковывался и с каталогом не сравнивался.

Количество аннотаций, распределение площадей и размеров объектов, декодирование масок, корректность всех ссылок `annotations.image_id`, уникальность ID и полнота треков не проверялись. Для этих выводов потребуется отдельный потоковый анализ аннотаций; загружать обучающий JSON целиком в память для первичного знакомства не требуется.
